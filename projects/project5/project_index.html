com-port-api

A phased plan to build a Windows C library for reliable COM port reading: start with direct, overlapped I/O access (comport), then add a shared daemon (comstream) for multi-client fan-out.

September 29, 2026   ·   Project   ·   Status: ✅ Operational

Project Goal: Build a C library that wraps the Windows serial port API so a program can read from a COM port reliably without busy-waiting. Provide two usage models: direct access (comport) for single-consumer programs, and a shared daemon (comstream) for multiple local applications that need the same stream.

Overview & Scope

Reading from a Windows COM port is deceptively tricky. Synchronous ReadFile either blocks forever or returns immediately with 0 bytes, forcing a busy-wait loop that burns CPU. Furthermore, COM ports are exclusive: only one process can hold a given port handle at a time.

This plan breaks the problem into two clear phases. Phase 1 builds a direct-access library (libcomport.a) using overlapped I/O and event-driven waiting. Phase 2 builds a shared daemon (comstreamd.exe) and client library (libcomstream.a) so multiple programs can consume the same serial stream via named pipes.

Within Scope: Windows serial API wrappers, overlapped (async) I/O, WaitCommEvent / EV_RXCHAR event handling, ClearCommError recovery, a ring buffer for non-blocking reads, a named-pipe daemon, and a multi-client fan-out protocol.

Out of scope: Cross-platform support (Linux/macOS), configurable parity/stop bits (planned for later), and a Windows service wrapper (on the roadmap).

Phase 1 · Direct COM Port Access (comport)

Phase 1

The first step is a library that lets a single C program open a COM port, read bytes, and close it—without polling. This phase is intentionally simple: no daemon, no shared access. It solves the core problem of reliable, event-driven serial reads.

Background

The Windows serial API is powerful but low-level. A naive read loop looks like this:

// The wrong way: busy-waiting
while (1) {
  DWORD n;
  ReadFile(h, buf, sizeof(buf), &n, NULL);
  if (n > 0) process(buf, n);
}
// This pins a CPU core at 100%.

The correct approach uses overlapped I/O with an event handle. The read is issued asynchronously and the thread sleeps in the kernel until WaitCommEvent signals EV_RXCHAR (a character has arrived). This yields ~0% idle CPU.

Why It Matters

ProblemNaive ApproachOverlapped I/O
CPU Usage 100% core, busy-waiting on ReadFile. ~0% idle CPU; thread sleeps in the kernel.
Latency Polling interval adds delay. Event fires immediately on EV_RXCHAR.
Reliability Missed bytes if the loop stalls. Driver RX buffer is drained promptly.
Error Recovery Silent failures on overrun/framing errors. ClearCommError recovers from line errors.
✅ Expected result: A library that reads bytes reliably from a COM port with negligible CPU usage, clean timeout semantics, and error recovery. This is the foundation for Phase 2.

Phase 1 Deliverables

  • serial.c / serial.h — internal serial port API.
  • comport.c / comport.h — public direct-access API.
  • libcomport.a — static library for linking into other projects.
  • readcom.exe — standalone diagnostic reader that prints incoming bytes as hex.
  • comport_example.exe — demo consumer showing the minimal read loop.

Phase 1 API Reference

Public API (comport.h):

comport_t *comport_open(const char *port, unsigned baud);
int comport_read(comport_t *c, void *buf, size_t len, unsigned timeout_ms);
int comport_write(comport_t *c, const void *buf, size_t len);
void comport_close(comport_t *c);
const char *comport_name(const comport_t *c);
  • comport_open — opens a port (e.g., "COM3") at a given baud rate. Returns NULL on failure.
  • comport_read — reads up to len bytes. Returns:
    • > 0 — bytes copied
    • 0 — timeout, no data
    • < 0 — port lost or unrecoverable error
    Pass COMPORT_WAIT_INFINITE to block until data arrives.
  • comport_write — writes bytes to the port.
  • comport_close — closes the port and frees resources.
  • comport_name — returns the port name (e.g., "COM3").

Phase 1 Integration Example

// minimal_consumer.c
#include "comport.h"
#include <stdio.h>

int main(void) {
  comport_t *c = comport_open("COM3", 115200);
  if (!c) return 1;

  unsigned char buf[256];
  while (1) {
    int n = comport_read(c, buf, sizeof(buf), 1000);
    if (n < 0) break;      /* port lost */
    if (n == 0) continue;  /* timeout */
    fwrite(buf, 1, n, stdout);
  }

  comport_close(c);
  return 0;
}

// Link against libcomport.a:
gcc -I inc minimal_consumer.c libcomport.a -lkernel32 -o my-app.exe

Phase 2 · Shared Daemon & Multi-Client Fan-Out (comstream)

Phase 2

Phase 1 proves that direct access works, but it has a critical limitation: Windows COM ports are exclusive. If your program holds the port open, no other program can read from it. Phase 2 solves this by introducing a daemon that owns the port and shares the byte stream via named pipes.

Background

A daemon (comstreamd.exe) opens the COM port and reads bytes continuously. It writes those bytes into a 1 MB ring buffer and serves them to clients over a named pipe (\\.\pipe\comstream). Each client gets its own cursor into the ring buffer, so a slow client falls behind without stalling the serial reader.

The client library (libcomstream.a) connects to the daemon's pipe and provides the same read semantics as comport. Multiple programs can connect simultaneously and all receive the same byte stream.

Architecture:

COM Port → comstreamd.exe → Ring Buffer → Named Pipe → Client(s)
  • COM Port — physical or virtual serial device (e.g., COM3).
  • comstreamd.exe — daemon that owns the port and reads bytes.
  • Ring Buffer — 1 MB circular buffer; oldest bytes overwritten when full.
  • Named Pipe — \\.\pipe\comstream for local IPC.
  • Client(s) — any number of programs using libcomstream.a.

Why a Ring Buffer?

The serial reader must never block. If it stalls, the driver's RX buffer fills and bytes are lost. A fixed-size ring buffer means the reader can always write (worst case, overwriting the oldest unread data), and each client tracks its own cursor. A slow client falls behind; the reader does not.

Sensor Fusion Algorithms (Multi-Client Scenarios)

ScenarioRecommended LibraryReason
Single Program comport Simplest path; no daemon overhead.
Multiple Programs comstream One port owner, many consumers.
Logging + Live View comstream One client logs, another visualizes.
Survives No Consumer comstream Daemon keeps reading even with zero clients.
✅ The key insight: You cannot share a Windows COM port. Either your program is the only consumer (use comport), or you run a daemon that owns the port and fans out the stream to any number of clients (use comstream).

Phase 2 API Reference

Client API (comstream.h):

comstream_t *comstream_open(const char *pipe_name, unsigned wait_ms);
int comstream_read(comstream_t *cs, void *buf, size_t len, unsigned timeout_ms);
void comstream_close(comstream_t *cs);
const char *comstream_pipe_name(const comstream_t *cs);
  • comstream_open — connects to the daemon's named pipe. Pass COMSTREAM_DEFAULT_PIPE for \\.\pipe\comstream.
  • comstream_read — same return semantics as comport_read. Pass COMSTREAM_WAIT_INFINITE to block forever.
  • comstream_close — disconnects from the pipe.
  • comstream_pipe_name — returns the pipe name.

Phase 2 Usage Example

# Terminal 1 — start the daemon
./comstreamd.exe COM3 115200
# [daemon] serial open on COM3 @ 115200
# [daemon] waiting for client...

# Terminal 2 — connect a consumer
#include "comstream.h"
#include <stdio.h>

int main(void) {
  comstream_t *cs = comstream_open(COMSTREAM_DEFAULT_PIPE, 5000);
  if (!cs) return 1;

  unsigned char buf[256];
  while (1) {
    int n = comstream_read(cs, buf, sizeof(buf), 1000);
    if (n < 0) break;
    if (n == 0) continue;
    fwrite(buf, 1, n, stdout);
  }

  comstream_close(cs);
  return 0;
}

# Start as many consumers as you want.
# They all receive the same stream.

Phase 3 (Future) · Production Hardening

Optional Extension

The core library works, but production use requires handling edge cases. This phase is not required for the core project but is documented for completeness.

  • Slow-Client Detection / Drop Policy: If a client falls too far behind, the daemon should detect this and either drop the client or skip ahead in the ring buffer.
  • Serial Reconnect: If the USB cable is unplugged, the daemon should attempt to reopen the port automatically.
  • Configurable Parity / Stop Bits: Add CLI flags and comport_open_ex for non-8N1 configurations.
  • Windows Service Wrapper: Run comstreamd.exe as a background service.
  • Optional Framing Protocol: Length-prefixed messages with timestamps.
  • Test Harness: Unit and integration tests for both libraries.
Slow-client policy (pseudocode):

if (client_cursor < write_cursor - RING_SIZE + margin):
  drop_client(client)
  log("client too slow, dropped")
  • client_cursor — the client's current read position in the ring buffer.
  • write_cursor — the daemon's current write position.
  • RING_SIZE — total capacity of the ring buffer (1 MB).
  • margin — safety buffer to avoid overwriting unread data.
