Project Planning · Accelerometer Position Tracking

A phased plan to track an object's position: start with a standalone accelerometer and double integration, then integrate a gyroscope and magnetometer for a full IMU sensor-fusion pipeline.

September 14, 2026   ·   Project Planning   ·   Status: 🚧 In Progress

Project Goal: Build a position-tracking system in phases. First, use a standalone accelerometer with double integration to get raw displacement. Then, add a gyroscope and magnetometer to correct orientation and gravity, enabling meaningful, real-world position tracking.

Overview & Scope

Tracking an object's position using only an accelerometer is theoretically done through a mathematical process called double integration. However, in real-world applications, doing this with a standalone accelerometer is incredibly difficult and notoriously inaccurate due to sensor noise, drift, and gravity.

This plan breaks the problem into two clear phases. Phase 1 sets up the accelerometer and implements the raw math to see firsthand why it fails on its own. Phase 2 introduces the gyroscope and magnetometer to solve the orientation and gravity problems, enabling a practical tracking solution.

Within Scope: Accelerometer setup, double integration math, noise/drift analysis, gyroscope and magnetometer integration, sensor fusion (Kalman/Madgwick), and orientation correction.

Out of scope: External absolute reference systems (GPS, Cellular, computer vision); these are noted as future extensions.

Phase 1 · Standalone Accelerometer & Double Integration

Phase 1

The first step is to set up a single accelerometer (e.g., an STM32LIS3DH, or a different dedicated 3-axis accelerometer) and implement the double integration math. This phase is intentionally limited to expose the fundamental problems: gravity bleed, noise, and exponential drift.

Background

An accelerometer measures proper acceleration, the acceleration it experiences relative to free-fall. When sitting still on a desk, it reads approximately 1g (9.8 m/s²) upward because the desk is pushing it up against gravity. To get position, you must integrate acceleration over time: once to get velocity, and again to get position. This is called double integration.

In discrete time (which is what a microcontroller does), you sample acceleration at fixed intervals (Δt) and accumulate. The math is simple, but the errors are not.

First Integration (Acceleration → Velocity):
vn = vn−1 + an · Δt

Second Integration (Velocity → Position):
pn = pn−1 + vn · Δt
  • vn — velocity at the current sample (m/s)
  • vn−1 — velocity at the previous sample (m/s)
  • an — measured acceleration at the current sample (m/s²)
  • pn — position at the current sample (m)
  • pn−1 — position at the previous sample (m)
  • Δt — time between samples (s), e.g., 0.01 s for 100 Hz

Why It Fails (Decently Researched Topic)

ProblemCauseEffect on Position
Gravity Bleed Earth's gravity (9.8 m/s²) projects onto X/Y axes when the sensor tilts. The sensor thinks it is permanently accelerating, causing runaway displacement.
Exponential Drift Minor random noise and bias in the accelerometer. Velocity error grows linearly; position error grows as t². A 0.01g bias yields meters of error in seconds.
Integration Error Discrete sampling, timing jitter, and numerical rounding. Accumulates over time, compounding the drift.
⚠️ Expected result: Within a few seconds, the computed position will diverge wildly from reality. This is not a bug, it is the fundamental limitation of standalone accelerometer tracking.

Phase 1 Deliverables

  • Accelerometer wired to the microcontroller (e.g., STM32, Arduino) via I²C or SPI.
  • Firmware that samples acceleration at a fixed rate (e.g., 100 Hz) and timestamps each sample.
  • Implementation of the double integration loop in C.
  • A data log or serial plot showing velocity and position over time, demonstrating drift.

Phase 1 Math Reference

Discrete integration loop (pseudocode):

dt = 0.01 // 100 Hz sample rate
velocity = 0
position = 0

loop:
  accel = read_accelerometer()
  velocity = velocity + (accel * dt)
  position = position + (velocity * dt)
  print(position)
  • dt — time step between samples (s)
  • accel — measured acceleration (m/s²)
  • velocity — accumulated velocity (m/s)
  • position — accumulated position (m)

Phase 2 · Adding Gyroscope & Magnetometer (Full IMU)

Phase 2

Phase 1 proves that a standalone accelerometer cannot track position. Phase 2 solves the orientation problem by adding a gyroscope (angular velocity) and a magnetometer (absolute heading). With these, you can determine the sensor's exact tilt and rotation, subtract gravity correctly, and isolate pure linear acceleration.

Background

A gyroscope measures angular velocity (how fast the sensor is rotating around each axis). By integrating angular velocity over time, you can track orientation, but it drifts slowly. A magnetometer measures the Earth's magnetic field, providing an absolute heading reference (like a compass). It is noisy but does not drift over time.

Sensor fusion combines these complementary sensors. A Kalman filter or Madgwick filter blends the fast-but-drifting gyroscope with the slow-but-absolute magnetometer and the gravity vector from the accelerometer. The result is a stable, accurate orientation estimate.

Once orientation is known, the gravity vector (9.8 m/s² downward in world coordinates) can be rotated into sensor coordinates and subtracted from the raw accelerometer reading. What remains is linear acceleration, the only thing you should integrate for position.

Orientation from gyroscope (integrated):
θn = θn−1 + ω · Δt

Gravity removal (world frame → sensor frame):
alinear = ameasured − RT · gworld
  • θn — orientation angle at the current sample (rad or deg)
  • θn−1 — orientation angle at the previous sample
  • ω — angular velocity from the gyroscope (rad/s)
  • Δt — time between samples (s)
  • alinear — linear acceleration after removing gravity (m/s²)
  • ameasured — raw accelerometer reading (m/s²)
  • R — rotation matrix from sensor frame to world frame (from sensor fusion)
  • RT — transpose of R (world frame to sensor frame)
  • gworld — gravity vector in world coordinates: [0, 0, −9.81] m/s²

Sensor Fusion Algorithms

AlgorithmTypeNotes
Madgwick Filter Complementary / gradient descent Lightweight, good for microcontrollers, open-source implementations available.
Mahony Filter Complementary (PI controller) Simpler than Kalman, well-suited for embedded systems.
Kalman Filter Optimal estimator More computationally intensive; can be extended to estimate velocity and position.
✅ The key insight: You cannot get position from an accelerometer alone. You must first solve orientation (with gyro + mag + fusion), then remove gravity, then integrate the remaining linear acceleration. Even then, drift is reduced but not eliminated, external references (GPS, Cellular) are still needed for long-term accuracy.

Phase 2 Deliverables

  • IMU with 3-axis accelerometer, gyroscope, and magnetometer (e.g., MPU9250, ICM-20948, LSM9DS1).
  • Sensor fusion implementation (Madgwick or Mahony) running on the microcontroller.
  • Gravity-compensated linear acceleration output.
  • Updated position tracking with significantly reduced drift compared to Phase 1.
  • Comparison plots: raw vs. fused orientation, and position drift before/after gravity removal.

Phase 2 Math Reference

Madgwick filter (simplified update):
q̇ = ½ · q ⊗ (0, ωgyro) − β · ∇f(q, aaccel, mmag)
  • q̇ — rate of change of the quaternion orientation
  • q — quaternion representing current orientation
  • ⊗ — quaternion multiplication
  • ωgyro — angular velocity from gyroscope (rad/s)
  • β — tuning parameter (trade-off between gyro and accel/mag trust)
  • ∇f — gradient of the objective function measuring accel/mag error
  • aaccel — accelerometer reading
  • mmag — magnetometer reading

Position integration after gravity removal:
vn = vn−1 + alinear · Δt
pn = pn−1 + vn · Δt
  • vn — velocity at current sample (m/s)
  • vn−1 — velocity at previous sample (m/s)
  • alinear — gravity-compensated linear acceleration (m/s²)
  • pn — position at current sample (m)
  • pn−1 — position at previous sample (m)
  • Δt — time between samples (s)

Phase 3 (Future) · External Reference Anchors

Optional Extension

Even with full sensor fusion, inertial position tracking drifts over time. Practical systems use periodic absolute references to reset accumulated error. This phase is not required for the core project but is documented for completeness.

  • GPS: Provides absolute outdoor position at ~1–10 Hz. Ideal for long-range tracking.
  • Computer Vision / Cameras: Tracks markers or infrared LEDs for indoor precision (as in VR headsets).
  • Zero Velocity Updates (ZUPT): When the sensor detects zero motion (e.g., a foot hitting the ground), velocity is forcibly reset to zero, eliminating accumulated drift.
ZUPT correction (simple):
if |alinear| < threshold and |ω| < threshold:
  v = 0 // reset velocity
  drift = 0 // optionally reset drift estimate
  • alinear — linear acceleration (m/s²)
  • ω — angular velocity (rad/s)
  • v — velocity (m/s)
  • threshold — small values below which motion is considered stopped
