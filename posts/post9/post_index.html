Kernels? I like popcorn!

What actually happens when you build a kernel, why embedded systems need their own, and the handful of ideas that make it all click.

October 8, 2026   |   Embedded Linux

Introduction

If you've used Linux for a while, you've probably installed a kernel update through your package manager. It downloads a file, reboots, and everything works. You never think about what's inside that file.

But on embedded systems such as routers, cameras, industrial controllers, and custom boards; you can't just grab the distro kernel and call it a day. You have to build one yourself. And the first time someone says "just build the kernel," it sounds like a magic trick (and not the magic smoke kind).

It isn't. It's a recipe, no more difficult than chicken and rice. This article explains the ideas behind that recipe, without going into the macros.

The Kernel Is Just a Program

At its core, the Linux kernel is a program. It's the first real program that runs when your system boots, and it's responsible for talking to hardware, managing memory, and giving other programs a place to run.

When you install Linux on your laptop, the kernel that comes with it is a generalist. It includes drivers for thousands of devices - network cards, webcams, printers, filesystems - because the distro maintainers don't know what hardware you'll plug in. It's a big, safe, everything-included kernel. Imagine you had to install a driver to use bluetooth on your phone, its easier to include everything and let people pick out what they done like.

An embedded system is the opposite. You know exactly what hardware is on the board. You know there's no printer, no webcam, no need for ten different filesystems. So why carry all that dead weight?

Why Embedded Systems Build Their Own

There are three practical reasons:

  • Storage is small. A general-purpose kernel can be several megabytes. On a device with 64 MB of flash, that's a huge chunk. A trimmed kernel might be under a megabyte.
  • Boot time matters. The more drivers the kernel probes at startup, the longer it takes to reach your application. A custom kernel only probes what's actually there.
  • Hardware is specific. Your board might use a chip that isn't supported in the mainline kernel, or you might need a vendor patch. You can't get that from a distro package.

So building your own kernel is really about control. You decide what goes in, and by extension, what stays out.

The One Idea That Matters: Configuration

If you remember nothing else from this article, remember this: a kernel build is just a configuration file and a compiler.

The configuration file is called .config. It's a plain text file full of lines like these: 

CONFIG_NET=y
CONFIG_USB_SUPPORT=m
CONFIG_EXT4_FS=y
# CONFIG_WIRELESS is not set

Each line answers a yes/no question about what the kernel should include:

  • y means "yes, compile this into the kernel."
  • m means "yes, but as a module that can be loaded later."
  • # ... is not set means "no, leave this out."

That's it. The entire build process reads this file and compiles exactly what you asked for. Everything else: the menus, the prompts, the defaults - is just a friendly way of generating this file. Gotta love plaintext config files!

How You Actually Make That File

You don't write .config by hand. That is unless you have a team dedicated to it. There are thousands of options. Instead, the kernel gives you tools to generate it.

The most common ones:

  • make defconfig — Asks the kernel for a sensible default configuration for your architecture. A starting point.
  • make menuconfig — Opens a text menu where you can browse and toggle options. This is how most people fine-tune a kernel.
  • make oldconfig — Takes an existing .config and updates it for a newer kernel version. Useful when upgrading.

For an embedded board, the vendor usually provides a defconfig file tailored to that board. You start with that, then adjust as needed.

Built-in vs. Module: The Only Real Decision

When you're configuring a kernel, you're mostly deciding one thing for each feature: should this be built in, or loaded as a module?

A built-in feature is compiled directly into the kernel image. It's always there, ready to go. This is what you want for anything the system needs to boot — storage drivers, the console, the interrupt controller.

A module is compiled as a separate file (ending in .ko) that lives on the filesystem. The kernel loads it when needed. This is good for things like USB devices or network cards that might not always be present, or that you want to load later.

On embedded systems, a common strategy is: build in the bare minimum to boot, and compile everything else as a module — or leave it out entirely.

The Mental Model

Here's the whole thing in one paragraph:

A kernel build is a configuration file plus a compiler. The configuration file says what goes in and what stays out. The compiler turns that into a kernel image and a set of modules. On embedded systems, you start from a vendor's default configuration, trim it down to what your board actually needs, and use a cross-compiler because your board isn't the same architecture as your build machine.

Everything else — the menus, the options, the build flags — is detail. The core idea is simple: you're telling the kernel what to include, and then compiling it.

Wrapping Up

If you've used Linux but never built a kernel, the gap is smaller than it looks. You already understand the concepts: configuration, compilation, dependencies. A kernel build just applies those concepts to a very large, very configurable program.

Start with make defconfig and make menuconfig on your own machine. Build a kernel for the computer you're sitting at. It won't be optimized, and it might not even boot — but it will demystify the process. Once you've done it for your laptop, doing it for an embedded board is just a matter of changing the architecture and starting from a different default configuration.
