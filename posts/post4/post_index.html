STM32 Development in VS Code

A complete guide to designing and programming STM32 products using VS Code, CubeMX, CMake, and Git (without fighting the IDE). Be water, program inbetween the user code sections.

September 12, 2026   |   STM32, VS Code, Embedded

Introduction

After years of using STM32CubeIDE, I wanted the speed and flexibility of VS Code for embedded work. While CubeIDE is perfectly good for developing STM32 applications, it is not fully supported by git (or at least not in a clean enough way that I was used to). Now I use VS Code for other non-embedded programming, and it would be really nice to be able to use it for pretty much all my projects if I can. Something about it being a good idea to put all your eggs in one basket or something? The new issue is that the STM32 toolchain wasn't designed around VS Code, so getting it set up took some trial and error. This guide documents the setup that actually works, including the fixes for the problems that the average user might miss during setup.

By the end you'll have a working VS Code environment for STM32 development, a project structure that plays well with Git, and a reliable way to flash your code to a real board.

Project Goal: Set up VS Code to design, build, flash, and version-control STM32 projects using CubeMX for peripheral configuration and CMake for the build system.

Installing the Toolchain

You need three separate pieces before VS Code can do anything useful:

ToolPurpose
STM32CubeMX Graphical peripheral and clock configuration
STM32CubeCLT Command-line toolchain: GCC, CMake, Ninja, OpenOCD, GDB
STM32CubeProgrammer Flashes firmware to the chip via ST-Link

Download all three from ST's website. Install them in a path without spaces or non-ASCII characters, while this is always good practice in my humble opinion. Especially considering GCC (which CMAKE uses) tends to parse the spaces as the user entering two serpeate paths... neat!

VS Code Extensions

Open VS Code and install these from the Extensions marketplace. The STMicroelectronics ones are modular, so you need several:

# Required
STM32Cube Core
STM32CubeIDE for Visual Studio Code
STM32Cube CMake Support
STM32Cube Debug STLink GDB Server

# Pick one C/C++ engine
STM32Cube clangd
# OR
ms-vscode.cpptools
Watch out: The first search result for "stm" may be an unrelated third-party extension. We are only dealing with the STMicroelectronics-published ones.

After installing, the extension will prompt you for the path to STM32CubeCLT. Point it at the install folder.

Creating the Project in CubeMX

CubeMX is where you configure peripherals, clocks, and pin assignments. The key setting is the toolchain:

# In CubeMX
Project Manager → Project → Toolchain/IDE → CMake

Do not pick Makefile or CubeIDE. CMake is what makes the project portable and Git-friendly.

Configure your GPIO, clocks, and peripherals visually. Give every pin a meaningful label, I shouldn't need to say this but it is just proper documentation. Yhese become macros in the generated code, so LED_GREEN is far better than a raw GPIO_PIN_5.

In Code Generator, check "Generate peripheral initialization as a pair of '.c/.h' files per peripheral" so your GPIO setup lives in its own file, this really makes it easier to manage.

Click GENERATE CODE.

Importing into VS Code

Open the project folder in VS Code, then use the STM32 extension to import it:

Ctrl+Shift+P → STM32: Import CMake Project

When prompted, select:

  • Board / Device: your exact MCU (e.g., STM32G0B1RET6)
  • Toolchain: GCC (GNU Compiler Collection)

Then click Configure. This runs CMake and generates compile_commands.json, which clangd needs for code intelligence.

Common gotcha: If you clicked Configure and nothing happened, run STM32: Setup STM32Cube project from the Command Palette instead. The button sometimes fails to trigger until the project has been discovered.

Writing Application Code

CubeMX generates Core/Src/main.c with empty while(1) loop and a set of special comment blocks. Only write code inside these blocks. Anything outside will be overwritten the next time you regenerate.

/* USER CODE BEGIN WHILE */
while (1)
{
    HAL_GPIO_TogglePin(LED_GREEN_GPIO_Port, LED_GREEN_Pin);
    HAL_Delay(500);
    /* USER CODE END WHILE */
}

The LED_GREEN_GPIO_Port and LED_GREEN_Pin macros come from the labels you set in CubeMX. If you rename a pin later, the code updates automatically on the next generation.

For anything more substantial such as a sensor driver, a state machine, create your own .c and .h files in Core/Src and Core/Inc. Keep them well away from the CubeMX-managed files.

Building the Project

Click the Build button in the VS Code status bar (the wrench icon), or from the Command Palette run CMake: Build. If you prefer the terminal:

cmake --build build/Debug

Output ends with Built target <your-project> when successful. The .elf file lands in build/Debug/.

Flashing to the Board

This is where most people get stuck. You cannot "run" the .elf file on your PC. It's compiled for the ARM Cortex-M core inside the STM32, not your x64 machine. Side-note: I realllly don't like that x86 is called x86 after the processor and nto x32 like the number of bits in the instructions. Windows will either ignore it or offer to open it with an app. Neither does anything useful.

You need to flash it. The most reliable method is the command-line programmer that comes with STM32CubeProgrammer:

STM32_Programmer_CLI -c port=SWD -w "D:/path/to/build/Debug/your-project.elf" -v -rst

Breaking that down:

  • -c port=SWD — connect to the ST-Link via SWD
  • -w <file> — write the .elf to flash
  • -v — verify after writing
  • -rst — reset the chip and run immediately

If the command isn't on your PATH, use the full path:

"C:/Program Files/STMicroelectronics/STM32Cube/STM32CubeProgrammer/bin/STM32_Programmer_CLI.exe" -c port=SWD -w "D:/path/to/build/Debug/your-project.elf" -v -rst
✅ Success looks like this:
• Memory Programming ...
• File download complete
• Application is running

If you see "No STM32 target found," the problem is the USB connection or the ST-Link driver, not your code.

Version Control with Git

Before you commit anything, create a .gitignore in the project root. Without it, your repository will be filled with build artifacts that regenerate every time you compile.

# Build output
build/
*.elf
*.bin
*.hex
*.map
*.o
*.d

# VS Code personal settings
.vscode/settings.json
.vscode/*.log
.vscode/ipch/

# OS files
.DS_Store
Thumbs.db

Then initialize and push:

git init -b main
git add .
git commit -m "Initial STM32 project"
git remote add origin https://github.com/YOUR_USERNAME/YOUR_REPO.git
git push -u origin main

What gets committed:

  • .ioc — CubeMX source of truth
  • CMakeLists.txt and CMakePresets.json
  • Core/ and Drivers/
  • Linker script and startup assembly
  • .vscode/launch.json (shared debug config)

What stays out: everything in build/.

Changing a GPIO Later

Never edit the generated initialization code by hand. To change a pin:

  1. Open the .ioc file in CubeMX
  2. Change the pin in the Pinout view
  3. Adjust its settings in System Core → GPIO
  4. Click GENERATE CODE

CubeMX will update MX_GPIO_Init() and the generated macros. Your code in the USER CODE blocks survives untouched. This is the entire reason those blocks exist.

Useful Commands

# Build the project
cmake --build build/Debug

# Flash the firmware
STM32_Programmer_CLI -c port=SWD -w "path/to/build/Debug/project.elf" -v -rst

# Verify the board is detected
STM32_Programmer_CLI -c port=SWD

# Check that clangd sees the compile commands
ls build/Debug/compile_commands.json

# Restart clangd if code intelligence stalls
Ctrl+Shift+P → clangd: Restart language server

Key Takeaways

  • Use CMake, not Makefile. It's the only toolchain that produces a Git-friendly project.
  • Only edit inside USER CODE blocks. Everything else gets overwritten.
  • Label your pins in CubeMX. The macros make your code readable and refactor-safe.
  • You cannot run an .elf on your PC. Flash it to the chip with STM32_Programmer_CLI.
  • Commit before regenerating. CubeMX changes should be their own commit, separate from hand-written code.
  • Ignore build/. Every artifact in it is regenerated on compile.

What's Next?

Once the basic workflow is stable, you can:

  1. Set up a dev branch and use feature branches for new work.
  2. Add GitHub Actions to auto-build the firmware on every push, catching broken commits before they merge.
  3. Tag releases (v0.1.0, v0.2.0) when you hit stable milestones.
  4. Add unit tests for your application logic and run them in CI.
