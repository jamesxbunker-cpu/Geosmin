Windows Pipes: A Practical Guide

Anonymous and named pipes, blocking vs overlapped I/O, and what I learned building my ComPort serial tool.

March 18, 2026  |  Windows, Systems Programming, IPC

Introduction

While building my ComPort project, a serial terminal and data logger for Windows, I hit a problem that every systems programmer eventually faces: I had one thread reading from the serial port, another thread writing to it, and a third thread updating the UI. How do I get data from the reader thread to the UI thread without locks, races, or a mess of shared buffers?

The answer, as it turns out, was Windows pipes. In this post, I'll explain what pipes are, the difference between anonymous and named pipes, how blocking and overlapped I/O change everything, and how I used them in ComPort to move serial data around safely.

What Is a Pipe?

A pipe is a chunk of kernel memory that behaves like a one-way (or two-way) stream of bytes. One end writes, the other end reads. The kernel handles the buffering, so the writer and reader don't have to know anything about each other. They just need a handle to their end of the pipe.

Why "pipe"? The mental model is a literal pipe: bytes go in one end and come out the other. You don't care how they're stored in between; the pipe just carries them. If you've ever used dir | findstr ".txt" in cmd.exe, you've already used a pipe. The output of dir flows into the input of findstr.

Windows gives you two flavors of pipe:

  • Anonymous pipes: unnamed, one-way, typically used between a parent and child process.
  • Named pipes: have a name in the filesystem namespace, can be one-way or duplex, and can be used between unrelated processes (even across a network).

Both are created with the same underlying mechanism, but they serve very different purposes.

Anonymous Pipes: Simple and Local

An anonymous pipe is created with a single call:

BOOL CreatePipe( PHANDLE hReadPipe, PHANDLE hWritePipe, LPSECURITY_ATTRIBUTES lpPipeAttributes, DWORD nSize );

Breaking down the parameters:

  • hReadPipe / hWritePipe: pointers to two HANDLE variables. The function fills them in with the read and write ends of the new pipe.
  • lpPipeAttributes: security attributes. The important field here is bInheritHandle. If you set it to TRUE, child processes can inherit the handle. This is how you pass a pipe to a child process you're about to spawn.
  • nSize: a hint for the buffer size. Pass 0 to let the system pick a default (usually 4 KB). The actual buffer may be larger.

Here's the catch: anonymous pipes are one-way only. If you need bidirectional communication between two processes, you need two anonymous pipes, one for each direction. And they can only be used between processes that share a parent-child relationship (or at least have a way to inherit handles). They are not named, so unrelated processes can't open them.

When to use anonymous pipes: When you're spawning a child process and want to capture its stdout or feed its stdin. Think CreateProcess with redirected output. That's anonymous pipes at work.

Named Pipes: The Full-Featured Option

A named pipe is created with CreateNamedPipe and lives at a path like \\.\pipe\MyPipeName. Because it has a name, any process that knows the name can open it. No parent-child relationship required.

HANDLE CreateNamedPipe( LPCTSTR lpName, DWORD dwOpenMode, DWORD dwPipeMode, DWORD nMaxInstances, DWORD nOutBufferSize, DWORD nInBufferSize, DWORD nDefaultTimeOut, LPSECURITY_ATTRIBUTES lpSecurityAttributes );

The parameters that matter most:

  • lpName: the pipe name, like \\.\pipe\comport_logger.
  • dwOpenMode: flags like PIPE_ACCESS_DUPLEX (two-way), PIPE_ACCESS_INBOUND, PIPE_ACCESS_OUTBOUND, and FILE_FLAG_OVERLAPPED for asynchronous I/O.
  • dwPipeMode: PIPE_TYPE_BYTE vs PIPE_TYPE_MESSAGE, and PIPE_READMODE_BYTE vs PIPE_READMODE_MESSAGE.
  • nMaxInstances: how many simultaneous connections the pipe allows. Use PIPE_UNLIMITED_INSTANCES for no limit.
  • nOutBufferSize / nInBufferSize: buffer sizes, again a hint.

Byte vs message mode is a subtle but important choice. In byte mode, the pipe is just a stream of bytes. Reads can return partial data. In message mode, each write is a discrete message, and a read returns exactly one message (or fails if the buffer is too small). For a serial port, byte mode is the natural fit because serial data is a stream.

The lifecycle of a named pipe server looks like this:

  1. CreateNamedPipe: create the first instance.
  2. ConnectNamedPipe: wait for a client to connect.
  3. ReadFile / WriteFile: exchange data.
  4. DisconnectNamedPipe: drop the client.
  5. CloseHandle: clean up.

A named pipe server typically runs a loop: create an instance, wait for a connection, service it, disconnect, and repeat. This is how services like SQL Server accept local connections.

Blocking vs Overlapped I/O

This is where a lot of people get stuck, and it's the single most important concept for using pipes (or serial ports, or sockets) effectively on Windows.

Blocking I/O is the default. When you call ReadFile on a blocking handle, the function does not return until data is available. Your thread sits there, doing nothing, waiting. This is fine for a simple console app, but terrible for a UI thread or a server handling multiple clients.

Overlapped I/O (also called asynchronous I/O) changes that. You open the handle with FILE_FLAG_OVERLAPPED, and then ReadFile returns immediately. The read happens in the background. You find out it's done through one of several mechanisms:

  • The OVERLAPPED structure's event. You wait on it with WaitForSingleObject.
  • An I/O completion port (IOCP), the scalable way to handle many operations at once.
  • A callback function, less common but possible.
The key insight: Overlapped I/O lets one thread manage many handles. Instead of dedicating a thread to each pipe (or serial port), you issue reads and wait for any of them to complete. This is how you scale to hundreds of connections without hundreds of threads.

The catch: Overlapped I/O is more complex to code. Every operation needs an OVERLAPPED structure, and you have to manage the lifetime of that structure until the operation completes. It's easy to introduce subtle bugs where you free the structure too early, or you forget to check GetLastError() == ERROR_IO_PENDING.

How I Used Pipes in ComPort

ComPort is a serial terminal and data logger. The core architecture looks like this:

  • Reader thread: continuously reads bytes from the COM port with ReadFile.
  • Writer thread: takes user input and writes it to the COM port.
  • UI thread: displays incoming data and accepts commands.

The problem: the reader thread has data, and the UI thread needs it. I could have used a shared buffer with a mutex, but that's error-prone and adds locking overhead. Instead, I used an anonymous pipe between the reader thread and the UI thread.

Here's the simplified flow:

// In the reader thread: BYTE buffer[1024]; DWORD bytesRead; while (ReadFile(hComPort, buffer, sizeof(buffer), &bytesRead, NULL)) { DWORD written; WriteFile(hPipeWrite, buffer, bytesRead, &written, NULL); } // In the UI thread: BYTE buffer[1024]; DWORD bytesRead; while (ReadFile(hPipeRead, buffer, sizeof(buffer), &bytesRead, NULL)) { // Append to the display AppendToConsole(buffer, bytesRead); }

Wait, but I just said anonymous pipes are between processes. How does this work within one process? The answer is that pipes work perfectly well within a single process. The two ends are just two handles. I created the pipe with CreatePipe, kept the read end for the UI thread, and passed the write end to the reader thread. No process spawning required.

The pipe gives me a clean, kernel-managed buffer between the two threads. The reader thread blocks on WriteFile if the pipe is full (which naturally throttles it), and the UI thread blocks on ReadFile until data arrives. No explicit synchronization needed.

Why not just use a thread-safe queue? I could have. But pipes gave me a few things for free:
  • Kernel-managed buffering, so no manual memory management.
  • Backpressure: if the UI can't keep up, the pipe fills and the reader blocks, preventing unbounded memory growth.
  • Blocking semantics: the UI thread just waits on a read, which is simpler than condition variables and locks.

For the command channel (UI to serial port), I used a second anonymous pipe in the opposite direction. Two pipes, two directions, clean and simple.

Pitfalls I Ran Into

No project goes perfectly, and pipes have a few sharp edges. Here are the ones that bit me:

  • Forgetting to close the write handle. If the write end of a pipe is still open somewhere, the read end will never see EOF. I had a bug where the UI thread's ReadFile would hang forever because a stray handle kept the pipe alive. The fix: close every handle exactly once, and use DuplicateHandle only when you actually need a copy.
  • Buffer size assumptions. I initially assumed a 4 KB pipe buffer would be enough for bursts of serial data. It wasn't. At 921600 baud, a few milliseconds of data can exceed that. The fix was to use a larger buffer and to never assume a WriteFile would complete without blocking.
  • Overlapped I/O structure lifetime. When I experimented with overlapped reads on the serial port, I made the classic mistake of allocating the OVERLAPPED structure on the stack. The call returned ERROR_IO_PENDING, the function returned, and the stack memory was reused before the operation completed. The fix: allocate OVERLAPPED structures on the heap (or as member variables) and free them only after GetOverlappedResult says the operation is done.
  • Message mode confusion. I tried using message mode for the command pipe, thinking it would preserve command boundaries. It did, but it also meant that if the reader's buffer was too small for a message, the read failed with ERROR_MORE_DATA and the rest of the message was lost. Byte mode with a length-prefix turned out to be more robust for my use case.

Quick Comparison

Feature Anonymous Pipe Named Pipe
Name None \\.\pipe\Name
Direction One-way One-way or duplex
Scope Local, typically parent-child Local or network, any process
Overlapped I/O Limited Full support
Best for Thread-to-thread data flow, child process redirection Client-server IPC, services, cross-process communication

The trade-off is clear: anonymous pipes are simpler but limited in scope, while named pipes are more flexible but require more setup and lifecycle management.

Summary

Windows pipes are a fundamental IPC primitive that every systems programmer should know. The key takeaways:

  • Anonymous pipes are perfect for simple, one-way data flow, especially between threads in the same process or between a parent and child process.
  • Named pipes are the full-featured option: named, duplex-capable, and usable between any processes on the same machine (or across a network).
  • Blocking I/O is simple but ties up a thread. Overlapped I/O is more complex but scales to many handles with few threads.
  • In ComPort, anonymous pipes gave me a clean, kernel-managed buffer between the serial reader thread and the UI thread, with no mutexes, no shared state, and no headaches.

If you're building anything on Windows that involves moving data between threads or processes, pipes should be in your toolbox. They're not glamorous, but they work.
